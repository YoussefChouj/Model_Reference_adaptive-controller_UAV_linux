Lesson 02 · The Rate loop, up close

Your Anti-Windup, Dissected

Brian Douglas showed you two ways to stop integrator windup: clamping and back-calculation. Your firmware appears to do clamping. Read it closely and you'll find it mostly doesn't — and that gap is your first real improvement.

This is the whole point of the mission in one lesson: never assume a feature works because it's there. Trace it. We'll walk every line of ComputePID() (pid.c:32–55), find what actually protects you, and mark exactly where a genuine anti-windup would bolt on behind a flag.

The windup problem (30-second recap)

The integrator sums error every tick to kill steady-state offset. But when the output is saturated — motor already maxed — pushing harder does nothing, yet the integrator keeps piling up error. When the setpoint is finally reached, that huge stored sum overshoots wildly before it bleeds off. That overshoot is windup. (Brian Douglas, Part 2.)

What your code claims to do

void ComputePID(PIDTypeDef *pPID) {
    pPID->E = pPID->Des - pPID->FB;                       // error

    if(((pPID->U <= pPID->UMax  && pPID->E > 0) ||        // [A] "not saturated high"?
        (pPID->U >= -pPID->UMax && pPID->E < 0))           // [A] "not saturated low"?
        && ABS(pPID->E) < pPID->EMin)                      // [B] integral separation
    {
        pPID->SumE += pPID->E;                            // accumulate
    }
    value_limit(pPID->SumE, -pPID->SumEMax, pPID->SumEMax); // [C] clamp accumulator
    pPID->Ui = pPID->Ki * pPID->SumE;
    value_limit(pPID->Ui, -pPID->UiMax, pPID->UiMax);      // [D] clamp I-term
    ...
    pPID->U = pPID->Up + pPID->Ui + pPID->Ud;
    value_limit(pPID->U, -pPID->UMax, pPID->UMax);        // [E] clamp total output
}

Four clamps and one gate. On paper: [A] is the "stop integrating when saturated" rule (Brian Douglas's clamping), [B] is integral separation, [C]/[D]/[E] are hard limits. Now let's check whether [A] actually fires.

The catch: gate [A] can never block

Look at what pPID->U is on entry. It was written only at line [E] last tick, and [E] clamped it into [-UMax, +UMax]. Nothing else in the firmware writes it. So this invariant always holds when the if runs:

-UMax  <=  pPID->U  <=  UMax        // guaranteed, every single tick

Now substitute:

  • If E > 0: U <= UMax is always true → clause [A] passes.
  • If E < 0: U >= -UMax is always true → clause [A] passes.

So [A] reduces to E ≠ 0 — it never actually detects saturation, because it compares U against the very limit it was just clamped to. The whole accumulation condition collapses to:

if ( ABS(pPID->E) < pPID->EMin )   // ...that's all [A]+[B] really amount to
Why this happens True clamping needs two different numbers: the output the controller wanted (pre-saturation) and the output the actuator allowed (post-saturation). Here they're the same variable clamped to the same constant, so their difference is always zero — no windup signal exists. Real saturation in your drone happens downstream at the motor mixer, which UMax never sees.
Your win What's actually protecting your rate loops from windup is [B] integral separation (only integrate when |E| < EMin — for the rate loops EMin is tiny, ~2 deg/s, so the integrator only works near steady state) plus [C] the accumulator clamp SumEMax. Not the saturation gate. You now know your firmware better than the wiki does.

Where your first improvement bolts on

This is a textbook flag-gated upgrade, and it lands at exactly one spot: right after line [E], where the pre- and post-clamp outputs both exist for one instant. That difference is the back-calculation signal Brian Douglas drew:

pPID->U = pPID->Up + pPID->Ui + pPID->Ud;
float u_presat = pPID->U;                          // what we wanted
value_limit(pPID->U, -pPID->UMax, pPID->UMax);      // what we're allowed

if (antiwindup_backcalc_on)                        // FLAG — default OFF = today
    pPID->SumE += pPID->Kt * (pPID->U - u_presat);  // bleed the integrator toward feasibility
Mission rule check (1) Which box? Rate PID. (2) Flag whose OFF = today? Yes — antiwindup_backcalc_on = 0 skips the line, behaviour is bit-identical to now. (3) Test ON vs OFF? Yes — sim/'s RatePID is parity with this function; drive a saturating step and compare overshoot. We'll build this in a later lesson.
